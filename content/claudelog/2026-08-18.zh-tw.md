### 遇到的問題

- **測試陷阱 1：git rename 檢測對短文件失敗 ⚠️**
  - 最初測試 fixture 只寫 10 行 body，git `-M20%` 閾值下也檢測不出 rename
  - 實際 rename-posts.js 跑的都是 30+ 行文章，body 微調 < 20% 行
  - 解決：測試 fixture 加到 40 段，模擬真實文章密度
- **測試陷阱 2：git mv vs 文件系統 mv ⚠️**
  - 最初用 `mv` 改文件名 + `writeFileSync` 覆蓋,git 不識別為 rename（變 A+D）
  - 解決：改用 `git mv` + 追加一行，模擬 rename-posts.js 真實操作
- **測試陷阱 3：Apple Git 的 `git rm` 副作用 ⚠️**
  - `git rm` 刪除 tracked 文件後，git 2.x 會清理空目錄
  - 後續 `writeFileSync` 寫新 SVG 時 ENOENT
  - 解決：測試 setup 時預放 `.gitkeep` 佔位文件
- **模塊化陷阱：頂層代碼副作用 ⚠️**
  - 把分類函數 `export` 給測試用後，import 時頂層 `if (!message) process.exit(1)` 會觸發
  - 解決：用 `pathToFileURL(process.argv[1]).href === import.meta.url` 守衛 CLI 代碼
- **未用 import ⚠️**
  - 測試文件 import 了 `join` from `'node:path'`，但實際用的是 `Array.prototype.join`
  - 自審時發現並清理，避免汙染

### 決策點

- **不改 `sync-covers.yml` 的調用方式**：它只傳 `--message` 不傳 `--message-fallback`，新腳本會讓 `fallback = --message`(原行為)。而且它的場景（cover IO）會被自動分類為 `chore(covers): ...`，永遠走不到 fallback 分支。比之前更精確 ✅
- **降級策略而非強制分類**：當改動是"rename + 改了正文"或"fm 注入 + 新建 cover"這種混合，分類不可靠，返回 null 讓 fallback 接住。不冒險亂分類
