## 维护记录（文章改名规则重做）

### 完成的工作

- 文章命名规则从 `YYYYMMDD-标题-hash.md` 改为 `YYYY-MM-DD.md`（无标题、无 hash）✅
  - `rename-posts.ts` 重写：文件名只由 front matter `date` 决定；同日多篇按「时刻 → title → 内容 hash」排序，首篇占裸名、其余 `-2`/`-3` 后缀（最多一天 16 篇）
  - 排序键全部取自内容、与当前文件名无关 —— 初版用旧文件名当最终排序键，首跑后 `-2` 后缀翻转排序（`2021-01-14.md` > `2021-01-14-2.md` 按字符序），规则自己互换名字死循环；`findBlockingCollisions` 挡住没丢数据，已改为内容 hash 定序
  - 正文 / 标题改动不再触发改名（旧规则 hash 取自正文，改一个字 URL 就变）；aliases 机制保留，旧 URL 全部保活
  - 存量 226 篇全部就地改名（`git mv` 保留历史），每篇自动追加旧 URL 到 `aliases`；`rename-posts-check` 复跑通过（0 篇待改）
  - 测试重写：新增同日排序 / 时刻优先 / 内容 hash 定序用例，`frontmatter.ts` 补 `toYyyyMmDd` / `timePart` 及用例；154 个测试仅剩 1 个 Windows 预存失败（check-dead-links 路径分隔符，与本次无关）
  - `AGENTS.md` / `README.md` / `bin/preflight.sh` 注释同步新规则

### 遇到的问题

- 本机 working copy 是 CRLF（`core.autocrlf=true`），front matter 解析器只认 LF，直接跑 rename 会把全部文章当「缺 title/date」跳过 ⚠️
  - 解决：用 `git cat-file blob HEAD:<path>` 把 `content/posts/` 整体重写为 LF（blob 本来就是 LF，重写后内容零差异，只是刷新 stat 缓存）；这是本机环境的老问题，顺手验证了之前的判断
- 两篇 2021-01-14《Composition Api》同日同题，触发上述排序互换死循环 ⚠️
  - 解决：排序键改为内容 hash 后，手工三步 `git mv` 换名对齐新规则（内容/aliases 不动）
